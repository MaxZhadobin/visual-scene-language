## 1. Vision

**VSL (Visual Scene Language)** — открытый формат и SDK для представления визуальных сцен в виде структурированных данных, понятных языковым моделям (LLM).

VSL — это **мост между визуальным миром** (экраны, интерфейсы, изображения) и **языковыми моделями**. Вместо того чтобы LLM "смотрела" на пиксели, VSL даёт ей семантическую структуру сцены в формате JSON, который модель уже умеет читать и понимать.

### Ключевая метафора

> VSL для LLM — это то же, что DOM для браузера. Браузер не парсит скриншот HTML-страницы — он работает с DOM-деревом. VSL даёт LLM "DOM экрана".

## 2. Problem Statement

### Проблема, которую решает VSL

Современные **computer use agents** (Anthropic Computer Use, OpenAI Operator, Google Mariner) работают с пикселями:

1. Делают скриншот экрана (1–2 MB JPEG/PNG)
2. Отправляют полный скриншот в LLM
3. LLM анализирует пиксели и принимает решение
4. Выполняет действие (клик, ввод, скролл)
5. Повторяют цикл

**Проблемы pixel-based подхода:**

| Проблема | Описание |
|----------|----------|
| 💰 **Дорого** | Каждый скриншот = 1–2 MB, отправляется на каждый запрос. При цикле из 20 шагов = 20–40 MB на одну задачу |
| 🐢 **Медленно** | Передача и обработка больших изображений добавляет latency |
| 🎯 **Неточность** | LLM плохо понимает семантику элементов из пикселей — путает кнопку с иконкой, не видит disabled state |
| 📦 **Нет стандарта** | Каждый провайдер решает проблему по-своему, нет открытого формата |
| 🔄 **Нет истории** | Нет версионирования состояний экрана — нельзя откатиться или сравнить |

### Почему это важно

Computer use agents — это будущее автоматизации. Но пока они работают как "слепой, которому показывают картинки" — дорого, медленно и ненадёжно. Нужен формат, который даёт LLM **понимание**, а не просто **пиксели**.

## 2.5 Why VSL? — Зачем нужна эта прокладка?

VSL — это **семантический транслятор** между экраном и LLM. Не просто прокладка, а мост, который превращает пиксели в понимание.

### Аналогия

| До VSL | После VSL |
|--------|-----------|
| LLM получает **скриншот** (1–2 MB пикселей) | LLM получает **JSON** (10–100 KB семантики) |
| LLM должен "угадать" что на экране | LLM получает готовую структуру |
| Каждый раз полный скриншот | Только diff изменений (экономия 60–80%) |
| Нет кэширования | Статические элементы кэшируются |

### 3 проблемы, которые решает VSL

**Проблема 1: LLM "слепой" без vision**
- Скриншот = дорого (1000+ токенов на изображение)
- Скриншот = медленно (передача, обработка)
- Скриншот = неточно (LLM может "галлюцинировать" элементы)

**Решение VSL:** семантическая структура + визуальные фрагменты только для сложных элементов.

**Проблема 2: DOM/A11y ≠ семантика**
- DOM-дерево = сырые данные (тысячи `<div>` без смысла)
- Accessibility API = лучше, но не всегда доступно
- LLM не понимает "почему эта кнопка здесь"

**Решение VSL:** Segmentation Engine извлекает семантику (кнопка, поле ввода, навигация) и представляет в компактном JSON.

**Проблема 3: Нет стандарта для computer use agents**
- Anthropic Computer Use = скриншоты
- OpenAI Operator = проприетарный формат
- Google Mariner = закрытая система

**Решение VSL:** открытый JSON-стандарт, model-agnostic, работает с любым LLM.

### Честные нюансы

**VSL НЕ заменяет vision models полностью:**
- Визуальные фрагменты всё равно нужны (изображения, canvas, сложные виджеты)
- VSL = гибрид (структура + визуал по запросу)

**VSL — это middleware, не конечный продукт:**
- Ценность VSL в экосистемном эффекте (как SQL для баз данных)
- Если VSL станет стандартом → все AI-агенты смогут работать с любым экраном

**VSL решает проблему "последней мили":**
- LLM уже умеет рассуждать
- Экран уже существует
- VSL = мост между ними (семантический транслятор)

### Итог

VSL — нужная и полезная прокладка, потому что:
1. ✅ Экономит токены (10–100 KB vs 1–2 MB)
2. ✅ Повышает точность (семантика вместо пикселей)
3. ✅ Ускоряет работу (diff вместо полного скриншота)
4. ✅ Даёт универсальность (model-agnostic)
5. ✅ Создаёт стандарт (экосистемный эффект)

Но VSL — не серебряная пуля:
- ⚠️ Нужен Segmentation Engine (сложная R&D задача)
- ⚠️ Визуальные фрагменты всё равно нужны
- ⚠️ Ценность VSL зависит от экосистемы (если никто не использует → бесполезно)

## 3. Solution

### Что такое VSL

VSL представляет экран как **JSON-дерево семантических объектов**:

{
  "canvas": {
    "width": 1440,
    "height": 900,
    "unit": "px",
    "origin": "top-left"
  },
  "objects": [
    {
      "id": "btn_submit",
      "type": "button",
      "label": "Отправить",
      "position": { "x": 600, "y": 800 },
      "size": { "width": 200, "height": 48 },
      "state": "enabled",
      "visual_ref": "emb_btn_submit_v3"
    },
    {
      "id": "input_email",
      "type": "text_field",
      "label": "Email",
      "placeholder": "you@example.com",
      "position": { "x": 400, "y": 600 },
      "size": { "width": 400, "height": 40 },
      "value": "",
      "state": "focused"
    }
  ]
}
### Как работает VSL SDK

VSL SDK работает как **middleware** между экраном и LLM:

┌──────────────────┐   ┌──────────────────────────────────────┐   ┌─────┐
│ DOM/Accessibility│──▶│  VSL SDK                             │──▶│ LLM │
│ API + Visual     │   │                                      │   │     │
│ Fragments        │   │  1. Извлечение структуры из DOM/A11y │   │     │
│                  │   │  2. Визуальные фрагменты для не-A11y │   │     │
│ (гибридный       │   │  3. Кэширование статических элементов│   │     │
│  источник)       │   │  4. Генерация диффа изменений        │   │     │
└──────────────────┘   └──────────────────────────────────────┘   └─────┘
                                                                     │
                                                                     ▼
                                                              ┌──────────┐
                                                              │ Action   │
                                                              │ (click,  │
                                                              │  type,   │
                                                              │  scroll) │
                                                              └──────────┘
### Ключевые механизмы

**1. Кэширование статических элементов**
- Фон, иконки, логотипы, статичные блоки — кэшируются после первого вызова
- Не перескриншотятся и не переотправляются
- Экономия: 60–80% данных после первого вызова

**2. Дифф-механизм**
- Каждый новый VSL-снэпшот содержит только **изменения** от предыдущего
- Статические элементы не передаются повторно
- Размер диффа: 10–100 KB вместо 1–2 MB полного скриншота

**3. Контекстные эмбеддинги**
- Каждый элемент имеет ссылку на визуальный фрагмент (эмбеддинг)
- LLM может работать только со структурой (быстро, дёшево)
- Или подгружать визуальные фрагменты по необходимости (когда нужна визуальная информация)

**4. Model-agnostic**
- VSL работает с **любым LLM**: GPT-4, Claude, Gemini, open-source модели
- Через промпт-инжиниринг, без fine-tuning
- JSON — нативный формат для всех современных LLM

**5. Lazy Text Loading** ([ROADMAP.md](./ROADMAP.md) M1.7, [ARCHITECTURE.md](./ARCHITECTURE.md) §3)
- Длинные тексты (статьи, параграфы > порога) **не включаются** в основной VSL JSON
- Вместо этого: `txt_preview` (первые ~50 символов) + `txt_ref: "tb_xxx"`
- Короткие тексты (кнопки, ссылки, labels) — остаются в `txt` как обычно
- Полные тексты кэшируются и отдаются по запросу через MCP tool `vsl_get_text_block(block_id)`
- Экономия: **80–90% токенов** для контентных страниц (статьи, блоги, документация)
- LLM в 95% случаев достаточно заголовков для навигации; полный текст — только по необходимости
- Принцип: **"pay only for what you need"** — аналогично lazy loading для visual fragments (`vf`)

**6. Prompt Injection Filter** (M1.8, [ARCHITECTURE.md](./ARCHITECTURE.md) §12.5)
- VSL как middleware перехватывает **весь текст** с экранов до отправки в LLM
- Фильтр работает **на входе Capture Layer** — сразу после извлечения текста из любого источника (DOM, raw HTML), **до** сегментации и упаковки в VSL JSON
- Библиотека паттернов — 3 уровня: bundled (в SDK), remote (CDN/GitHub, автозагрузка), custom (пользовательские через vsl.config.json)
- False positive strategy: confidence threshold + domain whitelist + user override
- Защита от скрытых инструкций в веб-контенте (`<div style="display:none">`, alt-тексты, meta-теги, raw HTML)
- Defense-in-depth: не заменяет sandboxing, но добавляет критический слой безопасности

## 4. Core Value Proposition

| Преимущество | Описание |
|--------------|----------|
| 💰 **10–100x дешевле** | После первого вызова — диффы вместо полных скриншотов (10–100 KB vs 1–2 MB) |
| 🎯 **Семантическое понимание** | LLM видит "кнопка Отправить (enabled)", а не набор пикселей |
| 🔄 **Версионирование состояний** | История изменений экрана как git diff — можно откатиться, сравнить |
| 🌐 **Model-agnostic** | Работает с любым LLM через промпт-инжиниринг, без fine-tuning |
| 📖 **Открытый формат** | JSON-спецификация, CC BY 4.0 — любой может использовать и расширять |
| 🧩 **Модульная архитектура** | VSL SDK — middleware, не требует замены существующих LLM-провайдеров |
| 📝 **Lazy Text Loading** | Длинные тексты не в JSON — кэшируются и отдаются по запросу (экономия 80–90% токенов) |
| 🛡️ **Prompt Injection Filter** | VSL как middleware фильтрует инъекции в веб-контенте до отправки в LLM |

## 5. Key Use Case: Computer Use Agent

### Основной сценарий

Автоматизация навигации по сайтам и приложениям через цикл:

DOM/accessibility API → VSL-представление + визуальные фрагменты → LLM принимает решение → действие → новый DOM/A11y snapshot → ...
### Примеры задач

- **Автоматизация веб-навигации**: заполнить форму, найти элемент, совершить покупку
- **Тестирование UI**: проверить доступность элементов, состояния, тексты
- **Accessibility audit**: найти элементы без label, проверить контрастность, навигацию с клавиатуры
- **Автоматизация рутинных задач**: перенести данные между системами, заполнить отчёт

### Почему VSL лучше pixel-based для computer use

| Аспект | Pixel-based (Anthropic) | VSL-based |
|--------|------------------------|-----------|
| Понимание элемента | "Это похоже на кнопку" | "Это button#submit, state=enabled" |
| Стоимость цикла | ~$0.05/шаг (полный скриншот) | ~$0.005/шаг (дифф после кэширования) |
| Точность действий | ~85% (путает элементы) | ~95% (семантическая идентификация) |
| История состояний | Нет | Да (версионирование) |
| Откат к предыдущему | Невозможен | Возможен (как git checkout) |

### Чтение веб-страниц для LLM: web_fetch на базе VSL (vsl_read_page)

Классический web_fetch (HTTP GET → readability → markdown) ненадёжен на современных сайтах:

- **SPA/CSR** — сайт отдаёт пустой HTML-shell, читать нечего (главная причина «ненадёжности»)
- **Шум** — меню, футеры, cookie-баннеры попадают в markdown
- **Нет интерактивности** — пагинация, аккордеоны, «показать ещё» недоступны
- **Потеря семантики** — типы и состояния элементов (button disabled, accordion expanded) не сохраняются
- **Нет кэширования** — каждое чтение возвращает полный контент заново, без диффов

**Решение: `vsl_read_page(url)`** — гибридный MCP-tool с автоматической стратегией (интеграция — [ROADMAP.md](./ROADMAP.md), M1.6):

- **Автоматическая стратегия** — агент НЕ выбирает режим: система сама определяет оптимальный путь
- **HTTP-first** — статические страницы читаются напрямую через HTTP GET + cheerio (миллисекунды), без браузера. Возвращает VSL JSON с семантической структурой (без точных координат bbox)

**Что даёт VSL по сравнению с markdown:**

- **Семантика объектов** — LLM видит `{t: button, st: disabled, act: [click]}`, а не плоский текст
- **Диффы на повторных чтениях** — −78.9% на идентичном повторе, −76.1% на мутации (замер M1.2); агентный цикл «прочитал → подействовал → перечитал» становится дешёвым
- **Интерактивное чтение** — через Action Model (23 действия): развернуть аккордеон, пролистать пагинацию, заполнить поиск — web_fetch превращается в web_interact
- **Автофильтрация** — script/style/display:none отсекаются при извлечении DOM

**Честное позиционирование:** это **дополнение** к классическому web_fetch, а **не замена**:

- Для чисто текстовых статей классический markdown компактнее и естественнее
- VSL-режим требует headless-браузер (Chromium, латентность первого снапшота 1–3s, ресурсоёмкий деплой)
- Первый VSL-снэпшот может быть больше markdown (атрибуты копируются verbatim) — нужен readable-режим с фильтром
- Headless-браузер чаще блокируется anti-bot системами

**Интеграция:** встраивается в M1.6 (MCP Server) рядом с `vsl_get_snapshot`/`vsl_get_diff` как ещё один tool. Смежный сценарий: [TARGET_AUDIENCE.md](./TARGET_AUDIENCE.md) §3.2 «Research agents» — VSL-web_fetch расширяет применение VSL за пределы computer use.

**Lazy Navigation (DEC-028):** При вызове `vsl_execute_action` система автоматически проверяет, находится ли браузер на URL из текущего snapshot. Если нет — автоматически навигирует на нужный URL. Это позволяет агенту сначала прочитать страницу через быстрый HTTP-путь, получить VSL JSON с семантической структурой, а затем выполнять действия — система сама запустит браузер и перейдёт на нужную страницу. Агенту НЕ нужно явно вызывать `vsl_navigate` перед выполнением действий.

## 6. Non-Goals (Чего VSL НЕ делает)

VSL — это **формат + SDK**, а не модель и не рендерер.

| VSL НЕ является | Пояснение |
|-----------------|-----------|
| ❌ Не заменяет vision models | Дополняет их — даёт семантику поверх пикселей |
| ❌ Не рендерит изображения | Описывает структуру; рендерер — отдельный компонент |
| ❌ Не привязан к LLM провайдеру | Model-agnostic: работает с любым через промпт |
| ❌ Не является UI-фреймворком | Не заменяет React, SwiftUI, Jetpack Compose |
| ❌ Не является дизайн-системой | Не определяет стили, цвета, типографику |
| ❌ Не требует fine-tuning LLM | Работает через промпт-инжиниринг |

## 8. Architecture Overview

> См. [ARCHITECTURE.md](./ARCHITECTURE.md) для детального описания.

### Высокоуровневая схема

┌─────────────────────────────────────────────────────────────┐
│                     VSL System                               │
│                                                              │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐ │
│  │ Capture  │──▶│ Segment  │──▶│  Build   │──▶│  Cache   │ │
│  │(DOM/A11y)│   │(elements)│   │ VSL JSON │   │ & Diff   │ │
│  └──────────┘   └──────────┘   └──────────┘   └──────────┘ │
│                                                     │        │
│                                                     ▼        │
│                                              ┌──────────┐   │
│                                              │   LLM    │   │
│                                              │(любая)   │   │
│                                              └──────────┘   │
│                                                     │        │
│                                                     ▼        │
│                                              ┌──────────┐   │
│                                              │  Action  │   │
│                                              │ Executor │   │
│                                              └──────────┘   │
└─────────────────────────────────────────────────────────────┘
### Ключевые компоненты

1. **Capture** — извлечение структуры из DOM/accessibility API + визуальные фрагменты для элементов, недоступных через A11y (изображения, canvas, кастомные виджеты)
2. **Segment** — разбиение на семантические объекты (из DOM/A11y + vision model для неструктурированных элементов)
3. **Build VSL JSON** — построение дерева объектов с координатами, типами, состояниями
4. **Cache & Diff** — кэширование статических элементов, генерация диффа
5. **LLM** — анализ VSL JSON и принятие решения (любая модель)
6. **Action Executor** — выполнение действия (click, type, scroll, navigate)

## 9. Platform Strategy
