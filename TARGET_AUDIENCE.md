## 1. Overview

VSL — это **инфраструктурный слой** для всех AI-агентов, работающих с экраном. Не узкопрофильная тула для разработчиков, а открытый стандарт представления визуальных сцен, который может использовать любой AI-агент для работы с компьютером и браузерами — для любых целей.

VSL встраивается в чужие продукты как SDK/middleware и не требует fine-tuning LLM — работает через промпт-инжиниринг с любым LLM (GPT-4, Claude, Gemini, open-source).

## 2. Target Audiences

### 2.1 Primary Audience — AI Agents (End Users of VSL)

**Кто это:**
Пользовательские AI-агенты, которые работают с компьютером и браузерами для выполнения задач. Это не разработчики — это сами агенты (или их операторы), которые используют VSL как "зрение" для понимания экрана.

**Примеры:**
- Персональные AI-ассистенты (покупки, бронирование, заполнение форм)
- Research agents (сбор информации с сайтов, мониторинг)
- Shopping agents (сравнение цен, поиск товаров)
- Workflow agents (автоматизация рутинных задач между приложениями)
- Customer support agents (навигация по CRM, заполнение тикетов)

**Pain points:**
- 💰 Дорого: каждый скриншот = 1–2 MB, при цикле из 20 шагов = 20–40 MB на задачу
- 🐢 Медленно: передача и обработка больших изображений добавляет latency
- 🎯 Неточно: LLM путает элементы, не видит disabled state, путает кнопку с иконкой
- 📦 Нет стандарта: каждый агент изобретает свой способ понимания экрана

**Value proposition:**
- **10–100x дешевле** после первого вызова (диффы 10–100 KB вместо полных скриншотов 1–2 MB)
- **Семантическое понимание**: агент видит "кнопка Отправить (enabled)", а не набор пикселей
- **Model-agnostic**: работает с любым LLM через промпт, без fine-tuning
- **Версионирование состояний**: история изменений экрана как git diff — можно откатиться, сравнить

---

### 2.2 Secondary Audience — AI Agent Developers (SDK Integrators)

**Кто это:**
Разработчики, которые встраивают VSL SDK в свои продукты. Они создают AI-агентов и нуждаются в стандартном способе представления экрана для своих моделей.

**Примеры:**
- Создатели computer use agents (конкуренты Anthropic Computer Use, OpenAI Operator)
- Разработчики RPA-решений (Robotic Process Automation)
- Команды, строящие автоматизаторы для конкретных доменов (e-commerce, finance, healthcare)
- Стартапы в области AI-автоматизации

**Pain points:**
- Нет открытого стандарта для представления экрана — каждый изобретает своё
- Проприетарные решения привязывают к конкретному LLM-провайдеру
- Нет кэширования и диффов — приходится оптимизировать вручную
- Нет версионирования состояний — нельзя откатиться или сравнить

**Value proposition:**
- **Открытый JSON-формат**: CC BY 4.0, любой может использовать и расширять
- **SDK/middleware**: встраивается в существующий стек, не требует замены LLM-провайдера
- **Кэширование и диффы**: из коробки, экономия 60–80% данных после первого вызова
- **Model-agnostic**: работает с OpenAI, Anthropic, Google, open-source — без vendor lock-in
- **Версионирование**: история состояний экрана как git diff

---

### 2.3 Tertiary Audience — QA/Test Automation Engineers

**Кто это:**
Автоматизаторы тестирования UI, которые нуждаются в стабильном семантическом представлении экрана для валидации.

**Примеры:**
- QA-инженеры в продуктовых командах
- Разработчики тестовых фреймворков (Selenium, Playwright, Cypress альтернативы)
- Команды, строящие visual regression testing
- Автоматизаторы acceptance testing

**Pain points:**
- Хрупкие селекторы (CSS, XPath) ломаются при любом изменении UI
- Нет семантического понимания состояния UI — только пиксели или DOM-селекторы
- Нет версионирования состояний — нельзя сравнить "было/стало"
- Visual regression testing требует ручного сравнения скриншотов

**Value proposition:**
- **Семантическая модель экрана**: стабильные идентификаторы элементов, не зависящие от CSS-классов
- **Версионирование состояний**: сравнение VSL-снэпшотов как git diff — автоматическое обнаружение изменений
- **Accessibility audit**: проверка label, контрастности, навигации с клавиатуры через структурированные данные
- **AI-powered testing**: LLM может анализировать VSL JSON и находить аномалии, пропущенные элементы, inconsistencies

---

### 2.4 Quaternary Audience — Accessibility Tool Developers

**Кто это:**
Разработчики инструментов для аудита и улучшения доступности (accessibility) веб-сайтов и приложений.

**Примеры:**
- Разработчики a11y-аудит инструментов (axe, Lighthouse альтернативы)
- Команды, строящие инструменты для генерации альтернативного текста
- Создатели инструментов для проверки WCAG-соответствия
- Исследователи в области accessibility

**Pain points:**
- Разрозненные данные из разных accessibility API (ARIA, OS-level A11y, DOM)
- Нет унифицированного представления a11y-данных
- Сложность интеграции с AI-моделями для автоматического аудита

**Value proposition:**
- **Унифицированный JSON-формат**: VSL объединяет данные из DOM, accessibility API, визуальных фрагментов
- **Семантическая идентификация**: каждый элемент имеет тип, label, state — готово для a11y-проверок
- **AI-ready**: LLM может анализировать VSL JSON и находить a11y-проблемы (отсутствующие labels, плохая контрастность, неправильная навигация)

## 3. Key Use Cases

### 3.1 Персональные AI-ассистенты для работы с браузером
**Сценарий**: пользователь просит AI-агента "забронировать столик в ресторане на завтра в 19:00 на 4 человека"
**Цикл**:
1. Агент получает VSL-представление страницы ресторана (DOM/A11y → JSON)
2. LLM анализирует структуру: находит форму бронирования, поля даты/времени/количества
3. Агент заполняет форму (действия: click, type)
4. Новый VSL-снэпшот → дифф (только изменившиеся элементы)
5. LLM подтверждает бронирование

**Роль VSL**: семантическое представление экрана + диффы для экономии токенов

### 3.2 Research agents для сбора информации
**Сценарий**: AI-агент собирает данные о ценах на товары с нескольких сайтов
**Цикл**:
1. Агент переходит на сайт → VSL-представление страницы
2. LLM находит таблицу товаров, извлекает цены
3. Переход на следующий сайт → дифф (статические элементы кэшированы)
4. LLM сравнивает цены, формирует отчёт

**Роль VSL**: кэширование статических элементов (шапка, футер, навигация), передача только динамического контента

### 3.3 Автоматизация рутинных задач между приложениями
**Сценарий**: перенести данные из CRM в spreadsheet
**Цикл**:
1. VSL-снэпшот CRM → LLM извлекает данные из таблицы
2. VSL-снэпшот spreadsheet → LLM находит целевые ячейки
3. Агент заполняет spreadsheet (действия: click, type)
4. Дифф-механизм подтверждает успешное заполнение

**Роль VSL**: семантическая идентификация элементов в разных приложениях, версионирование состояний

### 3.4 Тестирование UI с семантической валидацией
**Сценарий**: проверить, что все формы на сайте работают корректно
**Цикл**:
1. VSL-снэпшот формы → LLM проверяет наличие всех обязательных полей
2. Агент заполняет форму тестовыми данными
3. VSL-снэпшот после submit → LLM проверяет состояние (success/error message)
4. Сравнение VSL-снэпшотов: обнаружение неожиданных изменений UI

**Роль VSL**: стабильные идентификаторы элементов, версионирование состояний, AI-powered валидация

### 3.5 Accessibility audit
**Сценарий**: проверить сайт на соответствие WCAG 2.1
**Цикл**:
1. VSL-снэпшот страницы → извлечение всех интерактивных элементов
2. LLM проверяет: наличие labels, правильные роли, контрастность, навигация с клавиатуры
3. Генерация отчёта с рекомендациями

**Роль VSL**: унифицированное представление a11y-данных из DOM + accessibility API

## 4. Platform Strategy

### Phase 1: Web (MVP)
- **Платформа**: браузерное расширение или desktop-приложение с webview
- **Источники данных**: DOM + accessibility API браузера + визуальные фрагменты для сложных элементов
- **Интеграция**: OpenAI API / Anthropic API / любой LLM через промпт
- **Use cases**: веб-навигация, заполнение форм, сбор данных, тестирование веб-приложений
- **Целевая аудитория**: AI-агенты для работы с браузером, разработчики computer use agents

### Phase 2: Desktop
- **Платформа**: macOS / Windows / Linux
- **Источники данных**: OS-level accessibility API (macOS AX API, Windows UI Automation, Linux AT-SPI) + визуальные фрагменты
- **Интеграция**: кросс-приложная автоматизация
- **Use cases**: автоматизация десктопных приложений, перенос данных между программами
- **Целевая аудитория**: RPA-решения, персональные AI-ассистенты для десктопа

### Phase 3: Mobile
- **Платформа**: iOS / Android
- **Источники данных**: Accessibility API (VoiceOver на iOS, TalkBack на Android) + визуальные фрагменты
- **Интеграция**: мобильная автоматизация
- **Use cases**: автоматизация мобильных приложений, тестирование мобильных UI
- **Целевая аудитория**: мобильные AI-агенты, QA-автоматизаторы

## 5. Integration Patterns

### Pattern 1: AI Agent → VSL SDK → LLM API
**Описание**: AI-агент использует VSL SDK напрямую для получения семантического представления экрана.
**Пример**: персональный ассистент, который работает с браузером.
**Поток данных**:
Экран → VSL SDK (DOM/A11y → JSON + визуальные фрагменты) → LLM API → действие
### Pattern 2: Browser Extension → VSL SDK → LLM API
**Описание**: браузерное расширение извлекает DOM и accessibility данные, передаёт в VSL SDK.
**Пример**: расширение для автоматизации веб-навигации.
**Поток данных**:
Браузер → Extension (DOM/A11y) → VSL SDK → LLM API → действие в браузере
### Pattern 3: Desktop App → OS A11y API → VSL SDK → LLM API
**Описание**: десктопное приложение использует OS-level accessibility API для извлечения элементов.
**Пример**: RPA-решение для автоматизации десктопных приложений.
**Поток данных**:
ОС → A11y API → VSL SDK → LLM API → действие (click, type, scroll)
### Pattern 4: CI/CD Pipeline → VSL Snapshot → Automated Testing
**Описание**: CI/CD pipeline генерирует VSL-снэпшоты для автоматического тестирования UI.
**Пример**: visual regression testing, accessibility audit в CI.
**Поток данных**:
CI Pipeline → VSL Snapshot → сравнение с baseline → отчёт (pass/fail)
### Pattern 5: AI Agent → VSL SDK → Cache → LLM API (с кэшированием)
**Описание**: AI-агент использует кэширование для экономии токенов при повторяющихся задачах.
**Пример**: агент, который регулярно проверяет один и тот же сайт.
**Поток данных**:
Экран → VSL SDK → Cache (статические элементы) → Diff → LLM API → действие

## 6. Audience Priorities

| Audience | Размер | Готовность платить | Приоритет |
|----------|--------|---------------------|-----------|
| AI Agents (end users) | Огромный (все AI-агенты) | Через разработчиков | 🟢 Highest |
| AI Agent Developers | Средний (разработчики) | Высокая (SDK/middleware) | 🟢 High |
| QA/Test Automation | Средний (QA-инженеры) | Средняя (инструменты) | 🟡 Medium |
| Accessibility Tools | Малый (a11y-разработчики) | Низкая (open-source) | 🔵 Low |

**Стратегия**: начать с AI Agent Developers (Phase 1, Web), которые встраивают VSL в свои продукты. AI-агенты (end users) получают VSL через эти продукты. QA и Accessibility — дополнительные сегменты, которые выигрывают от того же формата.

## 7. Key Differentiators for Each Audience

| Audience | Почему VSL, а не альтернативы? |
|----------|--------------------------------|
| AI Agents | Дешевле (10–100x), точнее (семантика), model-agnostic (любой LLM) |
| AI Agent Developers | Открытый стандарт (CC BY 4.0), SDK/middleware, кэширование из коробки, нет vendor lock-in |
| QA Engineers | Стабильные идентификаторы (не CSS-селекторы), версионирование состояний, AI-powered валидация |
| Accessibility Tools | Унифицированный формат (DOM + A11y + визуал), AI-ready, open-source |
